### 為什麼

1. HTTP

網際網路上，機器溝通需要一個統一的規則，因此設計出來的目的是定義應用程式之間如何交換資料。一開始只是一群科學家有很多靜態文件要分享，需要一個簡單的方式來取得這些文件，因此HTTP的初始需求就是：取得資源，僅此而已。

2. HTTPS

當應用升級從學術文章交流到用戶隱私資料、金流時，你不會想要這些資料所有人都看得到，為了安全考量，資料在傳輸過程會加密。

### 是什麼

超文本傳輸協定，全名是HyperText Transfer Protocol，它制定了一套規則，定義了Client跟Server之間如何溝通，屬於應用層的協定，其本質就是一個無狀態的請求-回應模型。

    ┌─────────────────┐

    ├─────────────────┤
    │  6. 表現層       │
    ├─────────────────┤
    │  5. 會話層       │
    ├─────────────────┤

    ├─────────────────┤
    │  3. 網路層       │ ← IP
    ├─────────────────┤
    │  2. 資料鏈結層    │

    │  1. 實體層       │
    └─────────────────┘

> 一開始設計時並沒有狀態的概念，是一直發展下來才發現無狀態的好處。但演進過程其實也加入了很多狀態的設計，像是Cookie、Keep-Alive、多工串流、QUIC的連線ID。

HTTPS = HTTP + TLS/SSL

    ┌──────────────────────┐
    │    應用層：   HTTP
    ├────↓ 資料交給 TLS ────┤
    │  安全層：   TLS/SSL（在應用層和傳輸層之間）
    ├────↓ 加密後的資料 ─────┤
    │    傳輸層：   TCP
    └──────────────────────┘

### 延伸需求

- HTTP 的 Overhead 太高，光是 Header 就超過70+ bytes，真正的 Payload 可能只有 2 bytes。而 HTTP/2 除了讓一個 TCP 連線可以傳很多Stream(多工)，傳輸的單位變成是Frame，Size 大約只有 8 bytes 左右，比 HTTP/1 精簡很多，且多個 Frame 也可以在同一個 Stream 傳輸。

- HTTP 只能依賴 Client 主動發起請求，假如情境是 Server 有新資料時想更新給 Client: WebSocket

- 快還要更快: gRPC
